# LogHunter v2.0.0.4

Date: 2026-11-26

Patch on top of `v2.0.0.3`. Merges `feature/ioc-sweep-cdn`. Driven by a review of 105 Zendesk security / IIS / ALB / IP tickets (Aug–Nov 2026): `docs/ticket-gap-plan.md`, research in `docs/research/cdn/`.

## Included in this release

- IP sweep: any number of IPs, CIDR blocks and ranges across ALB and IIS logs.
- CDN and proxy range intelligence, refreshed in the app.
- CDN / proxy badges and a "Fronted by" banner in results.
- IIS client-IP resolution fix (right-to-left X-Forwarded-For, reserved ranges).
- ClaimedClient and X-Forwarded-For columns in IIS IP summary exports.
- ALB Start download button locked while a job runs.
- New `LogHunter.Tests` xUnit project (119 tests).

## IP sweep

Tickets showed the 10-IP cap and missing CIDR support as the only explicit complaints about LogHunter. One engineer wrote their own script for 34 targets, 16 of them CIDR ranges (3557308). Another needed 4+ runs and a CIDR calculator for a /27 (3523149).

- Input: pasted IPs, CIDR (v4/v6) and `start-end` ranges, `#` comments. IPv4 must be a full dotted quad: `12345` or `10.1` are rejected instead of being read as legacy IP forms.
- One job across up to 12 folders, one per environment. ALB vs IIS and `.gz` are detected per file. Corrupt archives are listed instead of stopping the sweep.
- IIS matches on the resolved client IP (X-Forwarded-For first).
- Per target: hits, first/last seen, matched IPs, top paths, status codes, hits per source.
- Scope block: files, lines, unparsed lines and observed time range per source.
- Reports: HTML (labels only, no file paths, caveats, Network column with CDN labels) and Excel (Targets, Matched IPs, Paths, Scope, Notes).
- Hand-offs: IP summary for top hits (with the swept folder pre-selected), Check reputation (single IPs plus matched IPs, CDN edges and health checkers skipped), Copy hit IPs.
- The form restores the last targets and folders after a reload.

Engine: `Utils/IpTargetParser` and `Utils/IpRangeSet` (sorted, non-overlapping segments, one binary search per lookup, overlapping targets all count). The same engine backs the CDN ranges.

## CDN and proxy ranges

Engineers were reporting Cloudflare edges as "top attacking IPs" (3476636: 20 of 20 were Cloudflare edges) and blocking them (3483741). The 12-month customer census: Cloudflare 144 orgs, Akamai 53, Imperva 31, Azure Front Door 15; Zscaler 50 and Netskope 16 as corporate proxies.

- Feeds, downloaded on first run and re-checked every 24 h in the background (Azure every 3 days):
  - Cloudflare (v4, v6)
  - AWS CloudFront and `CLOUDFRONT_ORIGIN_FACING`, Route 53 health checks
  - Akamai Origin IP ACL, plus AS20940 / AS16625 network ranges via RIPEstat, labelled "likely"
  - Imperva, Fastly, F5 Distributed Cloud (regional edges and CDN only)
  - Azure Front Door: `AzureFrontDoor.Backend`, found through the weekly service tags download link
  - Zscaler, as a corporate proxy
- Hard-coded small lists: Google Cloud load balancer to origin, Sucuri, Netskope.
- Broad cloud ranges (AMAZON, EC2, Cloudflare AS13335 as a whole) are deliberately not labelled. Attackers rent there, and WARP users sit there.
- Validation: parse check, private and too-wide ranges dropped, ±50 % size guard, HTTPS host check after redirects, 8 MB cap. A failing feed keeps its last good copy. The system proxy with default credentials is used.
- Storage: `config\ip-intel\` (manifest, raw feeds, `custom.txt` for pasted customer ranges).
- UI: "IP ranges" pill (age of the oldest feed) and `/ip-ranges` page (feeds table, Refresh now, customer ranges).
- Verdict: ≥ 80 % of a result's IPs on one CDN gives "Fronted by"; 50–80 % gives "Likely fronted by". A provider known only from network ranges never reaches "confirmed".

## IIS client IP

`IisClientIpResolver` took the leftmost public X-Forwarded-For hop, which the client controls: 3367120 reported a forged `106.106.198.131` instead of `219.153.113.105`. It also treated `0.0.0.0` as public: 3522405's `0.0.0.0,+82.158.196.58` resolved to `0.0.0.0`.

- The chain is now walked right to left. Private hops and known CDN edges are skipped. If every public hop is a CDN edge, the leftmost edge is reported (and badged).
- Single-hop lines never consult the CDN ranges, so IIS scan speed is unchanged.
- Non-public now includes `0.0.0.0/8`, `100.64.0.0/10`, `::`, IPv6 link-local and `fc00::/7`, and IPv4-mapped IPv6.
- This changes IIS IP summary, status pivot, burst and bytes results for chains with forged or CDN hops.
