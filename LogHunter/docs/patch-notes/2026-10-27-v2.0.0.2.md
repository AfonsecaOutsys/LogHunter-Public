Patch on top of `v2.0.0.1`.

## Included in this release

- Fixed the ALB download page sticking on a previous job's status.
- Added the `--trace` / `--debug` launch option.
- IIS Burst Patterns severity colors follow the severity score.

## ALB download page stuck on a previous job

Reported by operators pulling logs for one environment right after another, in the same tab: the job status panel kept showing the first job as `completed` with its file counts, while the second download ran unseen. Clicking Start again returned `An ALB download is already running.`

Cause:

- the page polls `/api/jobs/<id>` every 2 seconds and took the job id from whatever snapshot it rendered
- a poll reply for the old job that arrived after the start reply switched the page back to the old job, and every later poll followed it
- the server started the job while holding the job manager lock, and the job's first steps (`aws --version`, the first `aws s3 ls`) ran before the start request returned, so polls queued behind that lock and were released at the same moment as the start reply, which made the late reply likely
- the `409 already running` reply carried the running job's snapshot, but the page only showed the error text

Fix:

- the page tracks the job id it started (or found on page load) and drops status replies for any other job
- on `409 already running`, the page switches to the running job and shows the message
- repeated Start clicks while the start request is in flight are ignored
- the server registers the job under the lock and runs it on a background task, so Start returns immediately

Verified by forcing the race (status polls delayed 3 seconds, second download started while an old-job poll was in flight): `2.0.0.1` stays on the old job, `2.0.0.2` follows the new one.

Workaround on older builds: refresh the page (F5). On load the page asks the server for its current job.

## Trace mode (`--trace` / `--debug`)

Launch with `LogHunter.exe --web --trace` (or `--debug`). One JSON object per line is written to `logs\trace-<yyyyMMdd-HHmmss>-<pid>.jsonl` next to the exe. The path is printed on startup and shown in the web shell footer.

Recorded:

- app start (version, arguments, OS, machine), chosen mode, unhandled errors, exit
- every web request: begin/end with method, path, status and duration; JSON request and response bodies (size-bounded: long arrays and strings are cut)
- browser events: page loads, clicks, select/checkbox changes, every fetch with status and timing, tab visibility, JS errors, and ALB download page decisions (job tracked, stale reply ignored, start ignored)
- ALB download jobs: start/reject, every state/stage change, the child download process (command line, pid, exit code) and every output line
- ALB planner: AWS CLI path, resolved config and each `aws s3 ls` (URI, exit code, duration, line count, stderr)
- console mode: every menu selection

Never recorded: typed text from the browser, the AWS credentials block, and any field named like a secret, token, password, API key or credential. AWS key ids (`AKIA…`/`ASIA…`) and `AWS_*=` assignments are masked in any text that is recorded.

Trace mode is off by default and costs nothing when off.
